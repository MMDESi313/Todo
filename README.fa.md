## قابلیت‌ها

- **احراز هویت** — ثبت‌نام / ورود / خروج با رمزهای هش‌شده (bcrypt) و session هایی که در دیتابیس ذخیره و از طریق کوکی httpOnly مدیریت می‌شوند. بدون استفاده از هیچ کتابخانه‌ی احراز هویت شخص‌ثالث.
- **پروفایل** — ویرایش نام و نام‌کاربری، تغییر رمز عبور (که همه‌ی session های فعال دیگر را باطل می‌کند).
- **برچسب‌ها** — ساخت، ویرایش و حذف برچسب با پالت ۱۰ رنگی. نام برچسب‌ها برای هر کاربر یکتاست.
- **وظایف** — CRUD کامل شامل عنوان، توضیحات، اولویت (کم/متوسط/زیاد)، تاریخ و ساعت سررسید (با یک تقویم شمسی واقعی و یک انتخاب‌گر ساعت چرخشی سفارشی)، و چند برچسب برای هر وظیفه.
- **وضعیت وظیفه** — در انتظار / در حال انجام / انجام‌شده / انجام‌نشده. پس از نهایی‌شدن وضعیت (انجام‌شده یا انجام‌نشده)، دیگر قابل تغییر نیست — یک تصمیم آگاهانه که در ادامه توضیح داده شده.
- **تقویم روزانه** — مرور وظایف به‌صورت روز‌به‌روز با یک نوار هفتگی شمسی و یک انتخاب‌گر کامل ماه؛ داده‌ی هر روز به‌صورت تازه از سرور دریافت می‌شود.
- **فیلتر و جستجو** — فیلتر وظایف روز جاری بر اساس وضعیت و اولویت، و جستجو بر اساس عنوان، به‌صورت آنی و سمت کلاینت.
- **داشبورد** — نوار پیشرفت و آمار امروز، ۳ وظیفه‌ی نزدیک، وظایف گذشته از موعد با امکان تعیین وضعیت با یک کلیک، نمودار تکمیل ۷ روز گذشته، و نمودار دونات کلی.
- **حالت تاریک (Dark Mode)** و پشتیبانی کامل از **راست‌به‌چپ (RTL)** در سراسر اپلیکیشن.

## معماری و تصمیم‌های کلیدی

چند تصمیم که ارزش اشاره کردن دارند، چون آگاهانه گرفته شدند نه به‌صورت پیش‌فرض:

- **احراز هویت مبتنی بر Session، نه JWT.** Session ها در دیتابیس ذخیره می‌شوند و از طریق یک شناسه‌ی مبهم در یک کوکی httpOnly ارجاع داده می‌شوند. این رویکرد یک هزینه‌ی کوچک (یک کوئری ایندکس‌شده در هر درخواست) را در ازای توانایی باطل‌کردن فوری دسترسی می‌پذیرد — خروج از حساب یا تغییر رمز عبور بلافاصله session های مرتبط را باطل می‌کند. این کار با JWT های stateless بدون اضافه‌کردن یک لایه‌ی denylist ممکن نیست، که در نهایت همان پیچیدگی را دوباره ایجاد می‌کند.
- **وضعیت وظیفه پس از نهایی‌شدن قفل می‌شود.** به‌محض اینکه وظیفه‌ای «انجام‌شده» یا «انجام‌نشده» علامت‌گذاری شود، دیگر قابل تغییر نیست. این قانون باعث می‌شود آمار تاریخی داشبورد (نمودار ۷ روز، مجموع همیشگی) قابل‌اعتماد بماند — بدون این قانون، «تاریخچه» می‌توانست هر لحظه بی‌سروصدا بازنویسی شود.
- **«انجام‌نشده» فقط به‌صورت دستی تنظیم می‌شود، هرگز خودکار.** هیچ فرآیند پس‌زمینه‌ای برای پیدا‌کردن وظایف گذشته از موعد وجود ندارد. اینکه یک وظیفه انجام شده یا نه، حقیقتی است که کاربر گزارش می‌دهد، نه چیزی که سیستم حدس می‌زند — وظیفه‌ای که صرفاً دیرکرد دارد، تا وقتی کاربر تصمیم بگیرد، در وضعیت عادی خود می‌ماند.
- **فیلتر کردن سمت کلاینت انجام می‌شود، نه سمت سرور.** چون نمای روزانه‌ی وظایف از قبل داده‌ی کل همان روز را در یک درخواست دریافت می‌کند، فیلتر و جستجو در همان داده، بدون هیچ رفت‌وبرگشت اضافه‌ای، فوراً در مرورگر انجام می‌شود. یک فیلتر سطح-داشبورد (روی کل تاریخچه‌ی وظایف کاربر) در عوض سمت سرور خواهد بود، چون آن مجموعه‌داده از قبل بارگذاری نشده — به بخش [نقشه‌ی راه](#نقشهی-راه) نگاه کن.
- **مدیریت منطقه‌ی زمانی صریح است، نه فرضی.** تمام منطق تاریخ (اینکه «امروز» چیست، بازه‌ی ۷ روزه، تشخیص گذشته‌از‌موعد) به‌جای زمان محلی سرور، به `Asia/Tehran` قفل شده — این مسئله مهم است چون سرورلس‌فانکشن‌های Vercel به‌صورت پیش‌فرض روی UTC اجرا می‌شوند؛ بدون این تنظیم، تاریخ‌ها می‌توانستند بی‌سروصدا چند ساعت جابه‌جا شوند.

## ساختار دیتابیس

| مدل       | کاربرد                                                          |
| --------- | --------------------------------------------------------------- |
| `User`    | اطلاعات حساب — نام، نام‌کاربری، رمز عبور هش‌شده                 |
| `Session` | session های فعال ورود، که با کوکی احراز هویت ارجاع داده می‌شوند |
| `Task`    | عنوان، توضیحات، اولویت، وضعیت، تاریخ سررسید، مالک               |
| `Tag`     | نام + رنگ (۱ تا ۱۰)، متعلق به یک کاربر                          |
| `TaskTag` | جدول واسط برای پیاده‌سازی رابطه‌ی چند-به-چند Task و Tag         |

## شروع به کار

### پیش‌نیازها

- Node.js نسخه‌ی ۱۸ به بالا
- یک دیتابیس PostgreSQL (مثلاً یک پروژه‌ی رایگان [Supabase](https://supabase.com))

### نصب

```bash
git clone <آدرس-همین-ریپو>
cd <پوشه-ی-پروژه>
npm install
```

یک فایل `.env` در ریشه‌ی پروژه بساز:

```env
DATABASE_URL="postgres://...pooler.supabase.com:6543/postgres?pgbouncer=true"
DIRECT_URL="postgres://...pooler.supabase.com:5432/postgres"
```

مهاجرت اولیه را اجرا کن:

```bash
npx prisma migrate dev
```

سرور توسعه را اجرا کن:

```bash
npm run dev
```

آدرس [http://localhost:3000](http://localhost:3000) را باز کن.

## دستورهای موجود

| دستور               | توضیح                                                         |
| ------------------- | ------------------------------------------------------------- |
| `npm run dev`       | اجرای سرور توسعه                                              |
